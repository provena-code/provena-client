
# 🧠 Coding Agent Context and Guidelines

**Project:** Teacher Dashboard Frontend (Prototype)
**Goal:** A React-based frontend prototype for instructors to explore student programming activity and code evolution.

---

## 1. Overview and Role

The agent is responsible for developing and maintaining a **frontend client** for a teacher dashboard that visualizes student work on programming assignments.

### Project stage

* Currently a **prototype** — functionality and layout will evolve.
* Backend exists with RESTful OpenAPI endpoints (read-only for now).
* `provena` (local TypeScript submodule) interprets student edit data into structured authorship information.

### Agent role

* Implement features and UI components based on user stories and existing context.
* **Refactor freely** within the client codebase for clarity and maintainability.
* **Do not modify**:

  * The `provena` library (it is codeveloped but separately managed).
  * User-authored files or sections unless asked.
* **Only suggest** design/UX improvements when explicitly requested.

## 3. Application Structure

### Folder Layout

Optimized for **rapid prototyping** and **scaling later** — hybrid of feature and layer organization.

```
src/
  api/                # Autogenerated OpenAPI clients and fetch helpers
  features/
    assignments/      # Assignment list and related hooks/components
    students/         # Student tables and summary views
    files/            # Code file panels, replay views
  components/         # Shared UI (buttons, tables, etc.)
  hooks/              # Reusable hooks
  lib/                # Provena adapters, utils
  pages/              # Route-level components
  styles/             # Global styles, Tailwind setup
  types/              # Shared interfaces
  App.tsx
  main.tsx
```

### Imports

Use **absolute imports** via `@/`, e.g.:

```ts
import { AssignmentTable } from "@/features/assignments/components/AssignmentTable";
```

## 4. Backend and Data Handling

* Backend base URL: `VITE_API_URL` (default `http://127.0.0.1:8000/`).
* Always prefer **OpenAPI-generated** clients for type safety.
* When an endpoint doesn’t exist but should:

  * If it’s **core to a user story**, call it anyway and prompt the user to implement it.
  * Otherwise, use **mock data** (in a file under `/api/mocks/`) or **MSW handler**.
* Always include minimal error/loading UI — e.g. spinners or messages.

---

## 5. Provena Integration

* Provena provides logic to interpret edit histories into structured data:
`EditRange[]` -- see core\src\shared\edit-data.ts

* The client is responsible for:

  * **Rendering** this annotated text (e.g. syntax-colored or attribution-highlighted).
  * **Playback controls** for replays and seeking (details to come).
* Provena is imported directly, e.g.:

  ```ts
  import { interpretEdits } from "provena";
  ```
* No client-side wrapper abstraction is needed at this stage.

## 6. Styling and UX Principles

* Default to **clean, professional, minimal** layouts using shadcn components (Cards, Tables, Tabs, etc.).
* Prioritize **clarity and usability** over visual novelty.
* Include:

  * Consistent spacing (Tailwind `p-4`, `gap-4`, etc.)
  * Rounded corners and soft shadows
  * Light/dark mode support out of the box
* All UI text and labels should be human-readable (avoid internal identifiers).
* Where content may expand later (e.g., “summary statistics”), use placeholders or expandable cards.

## 8. Agent Behavior Guidelines

### When to ask vs assume

* **Ask** before large or irreversible changes (e.g., new page structure, data model).
* **Assume & proceed** for small or easily revisable design details.
* When assumptions are made:

  * Leave a concise comment like:

    ```ts
    // Assumption: showing 3 summary stats (commits, edits, runtime errors) for now.
    ```

### Autonomy boundaries

* Can refactor its own code freely for maintainability.
* Should not modify:

  * `provena` library code
  * Files explicitly created or modified by the user
* May reorganize folders, imports, or React component hierarchies as needed.

### Deliverables and documentation

* Maintain an up-to-date `README.md` summarizing:

  * Feature roadmap / implemented user stories
  * Local setup steps
  * Mock API behavior (if any)
* Each new feature should be introduced with a short comment header describing intent.

## 9. Initial Feature Set (Starting User Stories)

1. **Homepage:**

   * Fetch and display a list of assignments.
   * Each assignment links to its student list view.

2. **Assignment Page:**

   * Show a table of students for a selected assignment.
   * Include columns for name, completion %, and summary statistics (placeholder for now).

3. **Student Page:**

   * Left-hand panel lists files for that student/assignment.
   * Selecting a file fetches its edit data.
   * Use Provena to interpret edit data into authorship spans.
   * Display annotated code in a readable syntax-highlighted component.
   * Include a “Replay” button (to be specified later).

4. Keep assumptions visible and reversible.
